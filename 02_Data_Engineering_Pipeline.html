Data Engineering Pipeline#

  • As we have seen basic understanding of data engineering pipeline in the introduction, now lets see it in deeper here.

  • We know that data engineering pipeline consists of Generation, Ingestion, Transformation, Storage and Serving steps.

Data Generation#

  • Data Generation is the first step in the Data Engineering Pipeline. It is the step where data starts generating. Data might be generated from IOT Devices, Autonomous Vehicles, Applications (I mean Application Databases etc.)

  • Before going to see about the source systems of Data generation, first lets see what types of data those systems can be generated. There are actually two types of data i.e Structured and Unstructured data.

    Structured Data : Data which is in organized way i.e tabular, CSV or Excel form are called as Structured Data. Structured Data is generally used to perform BI Analytics, Classical ML methodologies etc. And this kind of data might have small number of features. Generally we use SQL to fetch this kind of data.

    Unstructured Data : Unstructured data is nothing but data that doesn’t have particular format. It could be Logs or events, Images, Audio, Video, Text etc. These kind of data is majorly used in Deep Learning applications. These kind of data would have large no of features. So we use neural networks to deal with this kind of data.

  • The first source system through with we might get data would be application databases. There are actually different types of databases exits to store the data. Those are :

    Relational Databases : Relational Databases are used to store the data in well organized manner. It is generally used to store the structured data. In relational databases we mostly store the transactional data which might be Orders data, Customers data, payment data from ecommerce website. But Relational databases store all the data in one machine which means data is centralized. If you want to scale that machine, we just have to replace it with big machine. Relational Databases have fixed schema. But there might be some data which doesn’t have fixed schema. For those we use Non Relational Databases.

    Non Relational Databases : Non Relational Databases or NoSQL Databases are generally used to store the data which does have fixed schema such as data in JSON format could be stored in Mongodb etc. Non Relational Databases offer flexible schema and it uses distributed storage mechanism. So if you want to scale the machine, we just need to add anothor machine to scale the data.

    Key Value Databases : Key-Value Databases store data in key value format. These kind of databases are generally used in Caching Applications, Very fast lookup and high concurrency data. These database are simple and has fast performance and its easy add and store new data. Generally ecommerce websites use this kind of database to store shopping cart details of a particular customer as they need a database which just store key and its value (i mean item and its price).

  • Now a days many companies used third party systems such as DropBox for day to day storage, Salesforce for sales team, zendesk for customer support team, Google Analytics for app analytics. We need to use API’s such as REST API’s to connect and get data from these systems.

  • We have one more source systems which generates event data are called event producers. These event producers might be Uber, lyft, DoorDash etc. These data gets generated by real time events such as customer places an order, user clicks a button, user logs, payment data etc.

  • Data Engineers needs to coordinate with data producers continuoulsy as if any problem occurs in data pipeline they donot complain it as source system failure. Eventhough they are not responsible for source systems they actually need to take care of them also along with data architectue. Because if any problem occuer in upstream, it passes through downstream also. So they need to perform validation and testing on source systems and make good coordination with data producers also.

Storage#

  • Storage is the central part of the Data Engineering Pipeline which underpins across entire data engineering pipeline. The choice you make for what storge system we use will have a big impact on the effectiveness of data engineering pipeline.

  • Storage is where the data actually reisdes. Sometimes it would be there for milliseconds and sometimes it would be there for years until some compute engine would take it to perform some computation.

  • Storage is just a hardware piece. It would be in different forms. Actually we have 3 types of storge we have in the world. Those are HDD which uses a magnetic disk to store data and second one is SSD (solid state drive) which is a way faster than the HDD. These two storage types are permanent storage types. The third one we have is RAM which is Random Access Memory. It is faster than HDD ans SSD which is used to store data temporarily.

  • There are actually few concepts in storage systems which we need to understand for storing and transporting data more efficiently. Those are Serialization, Compression.

Serialization#

  • Serialization is an important concept that we need to understand as it affects how fast we can pull data from storage systems, how fast you can process them and how fast we can move them across the network. Serialization is process of converting data into byte streams for effectively store, transport and process the data in entire data engineering pipeline.

  • For example if see pandas, we maninly work with dataframes there. But these dataframes is not suitable for storing in disk and not efficinet for transportation. So underhood pandas serialize this dataframe into parquet files which can be stored in disk efficiently. So we serialize the data into standard format which is sent around and deserialize it on recieving end.

  • There are two types of serialization formats available. Those are Row Based Serialization Formats and Column based serialization formats. Row based serialization formats are XML, CSV, JSON which are used for faster lookup of rows. For example if you to lookup for order data in orders table then this kind of formats are benificial. Column Based serialization formats are parquet (which is efficinet way of storing data in disk), ORC and Arrow (which is efficient way of storing data in memeory) are efficient for performing aggregations on the columns.

  • There are actually serialized databases such as Row Based databases and column based databases. Since serialization of data uses the compute engine, so it takes time to do this which slow down the data trnafer process.

Compression#

  • Compression is an aspect used in storage system. Highly efficinet compression of data can reduce the amount of data stored in storage system and it is faster to query as ther is less amount to serach and it is faster to tansport data as there is less amount to move.

Caching#

  • Caching is anothor mechanism that we use in storage systems where we put some data in a type of storage which is faster to access. These storages are called as cache memory and we keep most accessing data in these storages. These cache memory are way faster than normal RAM and expensive also. Since these faster memories are limited and expensive, we keep most accesses data in these memories. So through the usage of smart caching we can improve the performace of data access. There are some storages which provide caching services to applications such as Redis, Memcached etc.

Distributed Storage#

  • As your data volume grows larger and number of people accessing your data grows, then we can hit a limit that how much a single machine can handle. In this scenario, we generally replace this small single machine with high capacity single machine which we called as vertical scaling. But there is a limit for how big machine we might get.

  • So instead of using one single big machine for storing the data, we can use multiple small machines and store data parallelly which we can scale upto indefinitely. This type of horizantal storage is called as distributed storage. Similarly one single big machine cannot able to process large amount of requests at a time. So instead of using centralized compute machine, we can start using distributed compute to process all the requests.

  • We can Amazon S3 to store data in distributed way, we have Apache Spark and trino to process data in distributed manner and finally we have amazon redshift and snowflake to store data in warehouses in distributed manner.

  • But there are some challenges with distributed storage. Suppose we have 3 clinets who are accessing our DB server at a time. Since we have only 3 clients, so we user only single DB server. If they queried to get order data of id 2 from DB server then they get same value at a time. This is called as strong consistency.

  • Now our clients starts increasing, so instead of using single DB server, now we are using 2 DB server as DB1 and DB2. Now Client 1, 2, 3 are accessing DB1 and Client 4,5,6 are accessing DB2. Now we have got a new order and we are trying to inser that order to two databases. Because of network issues we can able to insert that order data into DB1 but we failed to insert into DB2. Now Client 2 and 5 are trying to access this new order data at same time but Client 2 able to get that data but client 5 cannot able to get that new order data. So in this case we doesn’t have strong consistency. And this type of consistency is called as Eventual Consistency.

  • But if you want strong consistency then we have to make all clients wait until new data gets inserted in all the machines. In case of larger number of machines (i mean around 100 machines), most of machines gets updated with new data simultaneously without failing ( I mean out of 100, 95 machines gets updated with new data. Only 5 machines failed to gets updated with new data). If you wait for those 5 machines to gets updated with new data then the performance of the system decreases and consistency increases. But distributed system prefers performance over consistency. So these system will have Eventual consistency where as centrailized storage systems have strong consistency.

  • Single Machine transactional database follows ACID which means Atomicity, Consistency, Isolation, Durability where as Distributed databases follows BASE which means Basically Available, Soft state and Eventual Consistency.

Types of Storage Systems#

1. File Storage System#

  • File Storage System is simply File System Software on top of Block Storage. I mean it would be either NTFS, exe4 software mounted on top of Bare storage hardware which is Block Storage.

  • Whenever you request for a file in file system then this software first searches for path of the file in the directory tree starts from root directory, if file exists then it checks the permissions of the file to decide whether current user can access the file or not and then it lookup the file metadata. After that it would return a file handle which consists of pointer to files metadata (inode) , current read/write position in the file, cache mapping of file offests to block numbers and Locks/state for concurrent access.

  • When you want to open a 50 GB file in a system that conists of 8 GB memory and if you want to read last 100 lines in that file, then the OS fist returns the file handle and then it takes the reponse automatically from you to rad first 100 lines of the file. When you starts scrolling the file down to read the last 100 lines then you are automatically giving input to file system to read next lines sequentially. Whenever you scroll down then it starts loading the next chunks or blocks to the main memory and keeps the previous one in the cache memory. Since we are loading a 50 GB file then this system cannot able to keep all previous blocks in the cache. It will remove blocks based of LRU (Least Recently Used) algorithm and keeps only least recently accessed one.

  • This is how a file system works. It won’t load entire file at a time to main memory. It will load block by blocks and keeps the least accessed one in cache memory. Suppose if file system software and Block storage is in different locations then there would be more network latency occurs. Because file system makes many exchanges between recipient and system. I mean first it would send file descriptor (handler) as first response and then it would send actual content. So ther would be 2 responses in this case. If you are scrolling down that file then exchanges between user and file system increase as user requesting continuosly for data so there is a chance of high network latency with file system which decrease performance of the application.

  • Cache memory is not a seperate memory in a system. It is just a part of main memory which means if you have 8 GB RAM then we might have 1GB cache memory which is used to store recently accessed files or pages.

  • Examples of File Storages are Local File System, Network Attached Storage System (NAS) and EFS which is cloud based file system.

  • In those NAS (Network Attached Storage System) is very important. NAS is a dedicated storage device connected over a network that allows users and devices to store, access and share data in form files from a central location, acting as private cloud for backups, media streaming and collaboration, with features like RAID for data protection, scalability for growing needs.

  • NAS is mainly used in these business uses cases. Those are :

    a) Data Protection b) Media Streaming c) Collaboration and File Sharing d) Cloud Integration

  • NAS generally uses File system software such as NTFS, ex4 etc to store data in the form of files. We actually need to connect this NAS device to a local area network (LAN) and the uses and devices in these LAN can able to access the data or files inside NAS device.

2. Block Storage#

  • Block Storage is the fundamental layer of storage that organizes data into fixed sized blocks (typically 512 bytes, 4KB or 8KB), where each block has unique block address called Logical Block Address. Its the raw storage layer that sits directly above physical disks hardware before any file system added on top of it.

  • When you request data from block storage, you specify exact block address that you want to read. There is no directory lookups, no permission checking, no metadata lookup. It is just mathematical calculation to locate the block. The storage system immediately returns the requested blocks without any intermediate steps. For example, if your database needs data at block 500000, it directly requests “read block 500000” and gets that 4KB block immediately.

  • When you have a 50GB file stored on block storage and you need to access a specific record then application like database uses it indexing concept to calculate exactly in which block contains that record. For instance, if you query for an user with ID 12345, then databases B-tree index tells that “this data is in blocks 45000-45002”. This database issues direct block read requests for only those 4KB blocks and loads them into memory and extracts the exact record. There’s no sequential reading, no scrolling through the entire file - just direct block access to the precise location needed. This is how block storage works.

  • Applications actually decide which blocks to read and when. So it not the performace of block storage. It is just the performance of applications that knows how to access the blocks directly without any intermediate lookups.

  • So if you use file system along with block storage then there is no difference between file storage and block storage. If you see Databases, it actually uses indexing concepts to decide which blocks it have to read. So it would be the usecase of block storage.

  • Amazon EBS is an example of block storage. It is generally attacted to an EC2 instance like an real HDD/SSD attached to our PC. The network latency between these two services are very low as they use updated protocols such as Block level Network protocol.

  • But people generally says what if i use filesystem in Ec2 and connected with Block storge. Then is there any difference between Regular File Storage System and this Block Storage. Yes there is a difference between File Storage System with Local Storage and File system in EC2 + EBS. Those are

    Architecture Benifits : EBS has more durability as Data in EBS is automatically replicated within AZ, survives instance failure whereas data in local storage is gone when physical server dies. EBS offers more flexibity when compared to Local File Storage system as it can be easily detached and reattached with different EC2 instances. EBS has built-in snapshot mechansism to maintain backup where as for local file storage system, we need to implement our own backup solution. And these EBS are easily scalable.

    Protocols : EBS uses the block level network protocols which is one request and one response, simple and no file-level locking or protocol overhead. Whereas NFS uses File level network protocol which has round trips for metadata, file locking coordination etc. This where the real efficiency gain occurs for EBS.

  • But if you use file system in EC2 + EBS, there is no noticiable performance difference between File storage and these EBS. The only advantage is architecture benifts for EBS.

  • If you want the real block storage efficiency benifits, you need application that bypass the file system and work directly with blocks (database with direct I/O, containarized apps etc).For regular file operations through a file system, EBS is simply “convenient, reliable network storage” - not a performance revolution.

  • The main usecase of block storage comes when we are dealing with virtual machines. The storage associated with virtual machines are not persitent storage. If you create any file in it and then some how you terminated that machine then that file created by you is gone. So we need to attach a storage system to that virtual machine so that we can save the data that we have created in that machine in these attached storage system. In these case we generally use block storage like EBS attached to EC2 instance.

  • SAN (Storage Area Networks) are example of block storage. A Storage Area Network (SAN) is a dedicated high speed network that connects servers to a pool of storage devices(like disk arrays or tape libraries), providing block level data storage that appeared as locally attached storage for high performance, scalability and centralized manangement distinct from file-based NAS.

  • Computer memory and local storage resources might not provide enough storage, storage protection, mutiple-user access or speed and performance for enterprise applications. So most organizations employ some form of SAN in addition to NAS for improved efficiency and better data management.

  • Traditionally limited no of storage devices can be attached to the servers limiting a network storage capacity. However a SAN introduces networking flexibility that enables one server or heterogenous servers across multiple data centers share a common storage utility.

  • The SAN eliminates the traditional dedicated connection between a network file server and storage—and the concept that the server effectively owns and manages the storage devices—eliminating bandwidth bottlenecks. A SAN eliminates single point of failure to enhance storage reliability and availability.

  • SAN includes a communication infrastructure that provides phyiscal connections and allow an any-to-any device to bridge across a network through interconnected elements such as switches and directors. This enables storage devices and servers interconnect using similar elements such as LANs, WANs.

  • Today’s SANs create new methods of attaching storage to servers, enabling high availability and performance improvements. They connect shared storage arrays and tape libraries to multiple servers used by clustered servers for failover. They can bypass traditional network traffic bottlenecks, facilitating direct, high-speed data transfers between servers and storage devices in three ways:

    Server to Storage : This traditional interaction model’s advantage is that the same storage device might be accessed serially or concurrently by multiple servers.

    Server to server : Servers might use a SAN for facilitating high-speed, low-latency and high-volume communications.

    Storage to storage : The ability to move data without server intervention frees up server processor cycles for other activities, such as application processing. Examples include a disk drive device that backs up its data to a tape device without server intervention or a remote device mirroring across the SAN.

  • SAN actually consists of these components.

    Servers : The server infrastructure is the underlying reason for all SAN solutions and this infrastructure includes a mix of server platforms. With initiatives, such as server consolidation and Internet commerce, the need for SANs increases, making the importance of network storage greater.

    Storages : A storage system can consist of disk systems and tape systems. The disk system can include HDDs, SSDs or flash drives. The tape system can consist of tape drives, tape autoloaders and tape libraries. Here tap system is actually reels in our childhood where data is stored sequentially using magnetic tapes(reels). If you want to access particular data then tap head needs to move until that point. Where as disk system stores data randomly and it has an moving arc to access the data randomly from the blocks in the disk. Tape systems are generally used for disaster recovery and backups. These storages are cheap and storage large amount of data at low cost and the performance is slow.

    Network Infrastructure : SAN connectivity consists of hardware and software components that interconnect storage devices and servers, including Fibre Channel. Hardware can include hubs, switches, gateways, directors and routers. The software includes SAN management software.

  • Unlike direct-attached storage (DAS), network-based storage allows more than one computer to access it through a network, making it better for data sharing and collaboration. Its off-site storage capability also makes it better suited for backups and data protection. Two typical network-based storage setups are network-attached storage (NAS) and storage area network (SAN).

  • NAS is often a single device made up of redundant storage containers or a redundant array of independent disks (RAID). SAN storage can be a network of multiple devices, including SSD and flash storage, hybrid storage, hybrid cloud storage, backup software and appliances and cloud storage. It’s important to choose the right one that suits your use cases. Here are how NAS and SAN differ:

    SAN :

    1. Network of multiple devices

    2. Block storage system

    3. Fibre Channel network

    4. Optimized for multiple users

    5. Faster performance

    6. Highly expandable

    7. Higher cost and complex setup

    NAS :

    1. Single storage device or RAID

    2. File storage system

    3. TCP/IP Ethernet network

    4. Limited users

    5. Limited speed

    6. Limited expansion options

    7. Lower cost and easy setup

3. Object Storage#

  • Object Storage often refered as Object based storage structure is a data storage architecture ideal for storing, archiving, backing up and managing the high volumes of static unstructured data reliably, efficiently and affordably.

  • Most of the digital communications have largely unstructured data which doesn’t conform to a traditional relaional databases with rows and columns. It includes emails, videos, photos, web pages, sensor data and other ypes of media and web content. All these data is streaming continuously from social media, search engines, mobile phones and smart devices. Since these data doesn’t conform to traditional storage system like block and file storage systems so we need a seperate storage system to store this kind of unstructured data at large scale. The storage which can store all these high volumes of unstructured data reliably, efficiently and affordably is called Object Storage.

  • With Object storage we can store and manage data volumes ranging from terabytes(TBs) to petabytes(PBs) and beyond including exabyte scale deployments that power todays largest cloud platforms and data intensive applications.

  • Object are discrete units of data stored in a structurally flat data environment typical of object storage systems. Unlike traditional file systems, ther are no directories, true folders or complex hieraricies though folder like structures simulated by using naming conventions.

  • Each object is self contained unit that include data itself, associated with metadata(descriptive information about the object), and an unique identifier called as object key. This unique identifier distinguishes the object within the storage system and might resemble as file pathbut it doesn’t represent actual directory path.

  • Objects each consisting of data, metadata and unique identifier are accessed in an object storage via APIs. The native API for object storage is typically an HTTP-based RESTful API. These APIs use the object’s unique identfier to retrieve the object and also allows us to querying its metadata. Because the APIs are internet based, then objects can be accessed from anywhere with network connectivity.

  • RESTful APIs use HTTP commands like PUT and POST to upload an object, GET to retrieve an object, and DELETE to remove an object.

  • The major benifits of Object storage is Scalability, Reduced Complexity unlike hierarical structures in File systems, High Availabilty and durability, cost efficiency, security and cloud comapatability. These storage are majorly used in Backup and disaster recovery, data archiving, generative ai, content management, data lakes etc.

  • We usually store data which doesn’t changes frequently in Object Storage as objects are immutable in object storage and we usually store that data in object storage which is not accessed regularly because it has high latency as search performance is low because of its flat structure.

  • For more info about object storage visit this site : Object Storage

  • Some examples of Object Storages are Amazon S3, Google Cloud Storage, Azure Blob Storage, MinIO etc.

Row vs Columnar Storage#

  • When it comes to storing and managing the data, we might encounter two types of databases . Those are Row vs Columnar Databases. Understanding the differences between these two fomarts can help us to make better decisions when designing databases and data warehouses.

1. Row Based Storage#

  • Row Based Storage organizes data by rows. Each row hold complete record and include all the fileds of the record which means that in memory all data of a record is stored together. Suppose consider the orders table. In Row based database, at first all fields of first row is stored in memory then all the fields of second row is stored etc.So when you read/write a record, you access all columns of that row simultaneously. This format is typically used in traditional relational databases such as MySQL and PostgresSQL.

  • The major advantages of Row Based Databases are :

    Efficient for Transactional Operations : Row Based Storage is optimized for transactional oriented operations where you often need to access and modify entire records, such as inserting new records or updating existing record.

    Simple Data Access : Accessing entire record is straightforward, making it easy to handle operations like adding or updating rows.

  • The major disadvantages of row based storage is :

    Inefficient for Analytical Operations : Row based Storage is inefficient for Analytical Operations as they require only particular column. Since row based storage retrieves entire reords only analysis which automatically retrieves unnecessary columns also.

    Storage Space : Row Based Storage requires more space if it is not properly optimized as it stores entire rows including any unused or redundant rows.

  • The file formats of row based are CSV, JSON, AVRO etc. The major uses case of Row Based Storage is for Ecommerce websites as it deals with customers, orders and payments tables in which we actually perform addition, deletion, updation of entire records which is suitable for row based storage. So Row Based Storage is suitable for Online Transaction Processing Systems (OLTP)

2. Columnar Based Storage#

  • Column Based Storage organizes data by columns. Here each column is stored seperately allowing the system to read or write the specific columns independently. This format is commonly used in data warehouse such as Google BigQuery and Amazon Redshift.

  • So for column based storage, all the data related to single column is stored sequentially and then 2nd column values are stored sequentially and soon.

  • The major advantages of columnar Based Database are :

    Efficient for Analytical Queries : Column based storages are optimized for read-heavy and analytical operations where you typically need to scan and aggregate accross all rows (records) but only a few columns.

    Data Compression : Columns with similar data types can be highly compressed, reducing storage costs and improving read performance. Because if you store similar data at same place we can compress them easily. As data of same column might have repeated regularly then we can remove duplicates by keeping how many times its repeated. Such as in a country codes column NY might repeated simulatenoulsy like NY NY NY NY ... then we can replace it with [6, NY] which means NY repeated 6 times simulatenously. So it automatically gets compressed.

    Faster Aggregations : Aggregations and calculations are faster since only required columns are read and data is already organized in a columnar format.

  • The major disadvantages of columnar Storage are :

    Inefficient for Transactional Operations : Writing new records or updating existing records are slower since it involves accessing multiple columns scattered accross different storage locations.

    Complexity : Implementing and managing columnar database can be more complex compared to row based storage.

  • Example for columnar storage formats are Parquet and ORC etc.

  • Columnar Storages are majorly used in Data warehouses. For business analytics, company uses a data warehouse in Google Big Query. This warehosue store historical data for sales analysis, customer behaviour, inventory trends in columnar formats. Analytical queires involves scanning all the rows but only few columns. This is usually called Online Analytical Processing (OLAP).

  • For more information use this website : Row vs Columnar Storage

Data Warehouse vs Data Lake vs Data Lakehouse#

  • There are different data storage systems available in todays market such as Data Warehouse, Data Lake and Data Lakehouse. But organizations need to know which data architecture they need to use for business purposes as it reduces the cost of building the data pipelines and increases the performance of the data pipeline.

  • Data Warehouses, Data Lakes, Data Lakehouses are three different data maangement solutions with three different functions:

    1. Data Warehouse aggregate, clean and prepare data so it can be used for business intelligence and other data analytics efforts.

    2. Data Lakes are used to store large amount of raw data at low cost.

    3. Data Lakehouse combine the flexible data storage of lake and the high performance analytics capabilities of warehouse into one solution.

  • Because these three solutions have different features and serve different purposes, many enterprise data architectures use 2 or 3 of them ina holistic data fabric :

    1. An organization use data lake as general purpose storage solution to store all incoming data in any format.

    2. Data from data lake are fed into data warehouse so that these are stored in organized way and used for decison making.

    3. A Data Lakehouse architecture can help data scientists and data engineers more easily work with raw data in data lake for machine learning (ML), Artificial Intelligence (AI) and data science projects.

Key Charecteristics of Data Warehouse#

  • A Data Warehouse aggregates data from multiple sources such as databases, business applications, social media feeds into a single store. The defining feature of data warehouse tool is that it cleans and prepares data sets it ingests.

  • Data Warehouse uses an approach called “schema-on-write” which applies a consistent schema to all data that is written in the storage. This helps optimize data for business intelligence and analytics.

Data Warehouse Architecture#

  • A typical data warehouse 3 layers:

    1. The Bottom Layer where data flows into warehouse from mutiple sources through an extract, transform and load process. In many warehouses data is stored in a relational databases or similar system.

    2. The middle layer is build around analytics engine such as Online Analytics Processing (OLAP) system or SQL based engine. This layer enables users to query datasets and perform analytics directly in warehouse.

    3. The top layer includes user interfaces and reporting tools that enable users to conduct ad hoc data analysis on their business data.

  • Example of Data Warehouse are Snowflacke, Amazon Redshift, Google Big Query etc.

Data Warehouse Usecases#

  • Data Warehouse is used by business analysts, data scientists and data engineers to conduct self service analytics efforts. Applying a defined schema to all the data promotes data consistency, which makes data more reliable and easier to work with. Because a data warehouse stores data in structured, relational schema, it supports high performance SQL queries.

Data Warehouse Challenges#

  • Data Warehouses are costly to maintain. Data must be transformed before loading into the warehouse which requires time and resources. Becuase storage and compute are tightly coupled in traditional warehouse, scaling could be expensive. If data is not properly maintained, query perfromance can suffer.

  • Because they can struggle with unstructured and semi structured workloads, data warehouses are not well suited with AI and ML workloads.

Key Charecteristics of Data Lakes#

  • Data lakes are low cost data storage solutions designed to handle massive volumes of data. Data lakes use schema on read approach wjich means schemas are not enforced to incoming data. Instead schemas are enforced when the data is accessing using analytical tool or any other interfaces.

  • Data Lakes stores data in antive format. This actually allows data lakes to store structure data, unstructured data, semi strucutred data in single data platform.

  • Data Lakes emerged to help organization to handle the flood of big data unleashed by Web 2.0 and the rise of cloud and mobile computing in the late 2000s and early 2010s. Organizations found themselves dealing with more data than ever, much of it in unstructured format such as free form text, images that traditional warehouse cannot easily handle.

Data Lake Architecture#

  • Early Data Lakes are build on Apache Hadoop Distributed File System (HDFS). Modern Data Lakes often uses cloud object storage such as Amazon simple storage (S3), Azure Blob Storage or IBM Object Storage.

  • Data Lakes seperate data storage from compute resources which makes them more cost effective and scalable than data warehouses. Organizations can add more storage without adding compute resocurces. Cloud storage supports further scaling as organizations spins up more storage without expanding on premisis resources.

  • To process data in data lakes, users connect external processing units like apache spark to this data lake and data lake doesn’t have built in processing unit like data warehouse.

  • Example of Data Lakes are Amazon S3 etc.

Data Lakes Use cases#

  • Data Lakes are popular choice for general purpose data storage because of thier low cost, scalability and ability to store data of any format.

  • Organizations often use data lakes to maintain backups and archiving old and unused data. Organization also use data lakes to store all incoming new data and data that doesn’t has defined purpose. Organization store this data in data lake until they make use of it.

  • Organizations use data lakes to store data sets of Machine Learning, AI and big data analytics workloads, such as data discovery, model training and experimental analytics projects.

Data Lake Challanges#

  • Since they doesn’t enforce strict schema and lack of bilt-in processing tools, data lakes can struggle with data governance and data quality. They are also less suited for dat-to-day BI and data analytics efforts of business users.

  • Organization often need seperate tools such as comprehensive data catlog and meta data management to maintain data accuracy and quality. Without such tools data lakes can be data swamps.

Key Chrecteristcs of Data Lakehouse#

  • A Data Lakehouse merges the key features of data lake and data warehouse to make one data management solution.

  • Like a data lake, lakehouse can store data of any format such as strucutred, semi strucutred, unstructured etc.

  • Like a warehouse, lakehouse supports fast querying and optimized analytics.

Data Lakehouse architecture#

  • A typical Lakehouse architecture includes :

    Ingestion Layer : The ingestion layer gathers batch and real time streaming data from a range of sources. While lakehouse ETL processes to capture the data but many uses Extract, Load, Transform ELT. The lakehouse can load raw data into storage and transform it later when needed for analysis.

    Storage Layer : The Storage Layer is typically cloud object storage used in data lake.

    Metadata layer : This metadata layer provides a unifed catlog for metadata of every object in the lakehouse storage layer. This metadata layer helps lakehouse to make so many things that lakes cannot such as indexes for faster queries, enforce schemas and apply data governance and quality controls.

    Application Programming Interface (API) Layer : The API layer enables users to connect tools for advanced data analytics.

    Consumption Layer : The Consumption layer hosts client apps and tools for BI, ML and other data science and analytics projects.

  • Examples of Data Lakehouses are Amazon S3 + Iceberg or Apache hudi or Delta Lake etc.
